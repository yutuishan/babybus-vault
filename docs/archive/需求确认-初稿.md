## 一、项目定位

面向**个人用户**的本地文档加密保险箱，Electron 桌面应用。核心承诺是：文件在磁盘上永远是密文，明文只在内存中短暂存在，且主密码一旦丢失数据不可恢复。

### 已确认的关键决策

| 维度 | 决策 |
|---|---|
| 产品形态 | Electron 桌面客户端 |
| 使用场景 | 个人本地加密存储（非团队协作、非外发 DRM） |
| 算法 | AES-256-GCM（国际标准）+ Argon2id 口令派生 |
| 技术栈 | Node.js + Electron，前端 React/Vue 待定 |
| 存储模型 | 目录镜像，文件名与目录结构一并加密（Cryptomator 式） |
| 打开方式 | 应用内置预览器，明文不落盘 |
| 解锁方式 | 主密码 + 密钥文件/U 盘（双因子，缺一不可） |
| 忘记密码 | 无后门，数据直接作废 |
| 平台 | Windows + macOS |
| 预览格式 | PDF、图片、纯文本/Markdown、Office 三件套、音视频 |
| 安全加固 | 闲置自动锁定 |
| 文件体量 | 小文件为主（<100MB） |

## 二、加密方案设计

### 2.1 三层密钥结构

```
主密码 ──Argon2id──┐
                   ├──HKDF──> KEK（密钥加密密钥）
密钥文件/U盘 ──────┘                │
                                   │ 加解密
                                   ▼
                              MK（主密钥，随机 256bit，存于 vault.keystore）
                                   │ 加解密
                                   ▼
                         文件内容 / 文件名密钥
```

**为什么分两层：** 用户改主密码时只需重新加密 MK（32 字节），不必重加密整个保险箱的全部文件。否则改一次密码要等几小时。

**为什么主密码和密钥文件缺一不可：** 两者各自派生出的密钥材料经 HKDF 合并，任缺其一都无法得到正确的 KEK。密钥文件丢失 = 数据丢失，需在设计上强制用户备份。

### 2.2 Argon2id 参数建议

```
memory:      64 MiB（可调，根据机器内存自适应）
iterations:  3
parallelism: 4
salt:        16 字节随机，随 vault 一起存储
```

目标是单次派生耗时 0.5~1 秒——用户体验可接受，同时把离线爆破成本抬高几个数量级。

### 2.3 文件内容加密

- 算法：AES-256-GCM
- 分块：32 KiB 为一块，每块独立加密
- **每块必须使用独立 nonce**：采用 `随机 96bit base nonce + 块序号` 派生，禁止复用（GCM 下 nonce 复用会导致认证密钥直接泄露，是最致命的误用）
- 文件头作为 AAD 参与认证，防止块被重排、截断、跨文件拼接
- 文件头存明文元数据：格式版本号、分块大小、base nonce、原始大小

### 2.4 文件名与目录结构加密

- 文件名加密需**确定性**（同一文件名始终映射到同一密文），否则无法做路径查找 → 采用 AES-SIV 或 `AES-CTR(HMAC(名称))`
- 密文文件名存为 base64url / base32，避免跨平台大小写与非法字符问题
- 目录树扁平化：真实目录结构打散为哈希分桶（如 `d/ab/cdef...`），避免泄露目录层级和文件数量分布
- 目录元数据单独加密存储，明文只暴露"有若干目录项"

### 2.5 明文绝不落盘

内置预览器直接消费内存中的明文 Buffer：

- PDF → pdf.js 从内存 Buffer 渲染
- Office → 转 PDF 后走 PDF 通道，或调用渲染库直接读 Buffer
- 音视频 → 通过自定义 protocol（`vault://`）以流方式喂给 `<video>`，不经由临时文件

> 这一条是本项目与普通"加密压缩"工具的本质区别，也是实现难度的主要来源。Office 预览是其中工作量最大的一环。

## 三、安全架构（Electron 侧）

| 措施 | 说明 |
|---|---|
| `contextIsolation: true` `nodeIntegration: false` | 渲染进程拿不到 Node 能力 |
| 密钥只在主进程 | 渲染进程通过 IPC 请求解密后的内容，永远拿不到 MK |
| CSP 严格策略 | 禁止加载任何远程资源，防止被注入外泄 |
| 系统休眠/锁屏即锁定 | 监听 `suspend` / `lock-screen` 事件 |
| 闲置自动锁定 | 默认 5 分钟无操作锁定（可配置） |
| 锁定时主动清零 | `Buffer.fill(0)` 清空内存中的 MK，不等 GC |

## 四、风险与待确认项

### ⚠️ 矛盾一：音视频预览 vs 小文件体量

你选择了「音视频预览」，又选择了「小文件为主 < 100MB」。这两个在现实中大概率冲突：
- 一段 1080p 视频轻松超过 100MB
- 视频若整文件解密进内存，1GB 文件就需要 1GB 常驻内存，Electron 会崩

**建议二选一：**
1. 保留音视频预览 → 必须做流式解密（`vault://` 协议边解密边播），大文件分块流式处理
2. 砍掉音视频预览 → 保持整文件内存加解密，实现简单很多

我倾向保留音视频但做流式——因为流式分块结构本来就是 2.3 节的设计，不算额外成本，**只需要补一个自定义 protocol 处理器**。

### ⚠️ 风险二：无后门 + 强制作废是双刃剑

这个策略安全性最高，但要接受一个后果：**客诉会非常难看**。用户会把"我忘了密码"当作产品 bug，而不会认为是自己的责任。

**建议至少做一件事**：创建保险箱时让用户手抄/导出一段恢复码并二次确认"我已妥善保存"。这不算后门（服务端不存任何东西），但能显著减少纠纷。你之前选了"无后门，数据直接作废"，是否加这一个保险，请确认。

### ⚠️ 风险三：防截屏未纳入

你没选防截屏，意味着系统级截图、录屏、以及任何远程桌面工具都能捕获预览窗口内容。需要明确：这是**产品定位上的取舍**（保护"磁盘上的密文"而非"屏幕上的明文"），还是遗漏？

- 若只是防磁盘泄露 → 现状 OK
- 若要防屏幕泄露 → 需加 Windows `SetWindowDisplayAffinity`，macOS 侧能力受限（只能做到窗口隐藏，做不到阻止截图）

### 待补的小问题

1. 主密码错误次数限制？是否需要防爆破锁定/延时？
2. 是否需要"最近文件"列表？会泄露用户行为痕迹，建议默认关闭
3. 是否需要保险箱自毁（多次密码失败后擦除 MK）？
4. 界面语言：仅中文 / 中英双语？
5. macOS 是否有开发者账号（签名公证需要，未签名会被 Gatekeeper 拦截）？
