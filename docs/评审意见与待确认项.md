### ⚠️ P0-1 复核更正 —— 更正本身又被实测推翻（结论：回到你原本选的 A）

这里有一处曲折，最终结论以**实测**为准：

1. **我的原始意见**：Node 的 crypto 没有 Argon2 → 建议引入 hash-wasm（你据此选了 A）。
2. **我的第一次更正**（错误）：Node 24.7 起有 `crypto.argon2Sync`，Electron 43 内置 Node 24.17 →
   我判断"开箱可用"，把方案改成内置优先，hash-wasm 降级为末选。
3. **M1 实测推翻了第 2 条**。在真实 Electron 43.7.0 中：

   ```
   [env]   Electron 43.7.0 / Node 24.21.0 / Chromium 150
   [kdf]   node argon2id : 不可用（Argon2 algorithm not supported）
   [kdf]   wasm argon2id : 448~491ms  ✅
   [kdf]   scrypt        : 314~327ms
   ```

   **根因：Electron 链接 BoringSSL（Chromium 系），没有 OpenSSL 3.5+ 的 Argon2 KDF。**
   于是 `typeof crypto.argon2Sync === 'function'` 为真，一调用就抛
   `ERR_CRYPTO_ARGON2_NOT_SUPPORTED`。

**最终方案 = 你原本选的 A（hash-wasm），只是保留内置作为更快时的首选：**

```
Node 内置 argon2id（236ms）→ hash-wasm argon2id（430ms）→ scrypt（327ms）
```

Electron 下实际走 hash-wasm。已验证 hash-wasm 与内置实现**逐字节一致**，
换机器不会导致打不开库。

> **方法论教训（比结论更重要）：能力探测必须实跑一次。**
> 只判断 `typeof fn === 'function'` 在 Electron 里会被 BoringSSL 坑——
> API 存在 ≠ 算法可用。这条已写进基线 §5.1。

### 该决策的连带影响（已一并写入基线）

1. 首次运行不再是"设置主密码"，而是先进**文件库选择界面**（新建 / 打开）。
2. `data/vault/` 结构取消，文件库根目录即用户选中的文件夹；`config.json` 降级为纯应用配置（存最近文件库列表 + 界面偏好），优先写在程序同级目录。
3. 更新流程不再需要"复制 `data/` 目录"，更新后直接「打开文件库」选中原位置。
4. 新增两条必须实现的防护措施（已写入开发文档 §4 / §12）：
   - **新建前必须校验目标文件夹是否已是文件库**，存在 `vault.meta` 则强制走"打开"流程 —— 否则用户误点新建会覆盖 `vault.meta`，数据永久丢失。
   - **路径失效时绝不静默新建**，只能提示"未找到"并提供重新选择位置。
5. macOS 端不再存在往 `.app` 内写用户数据的问题，P0-5 原本的风险点自然消解；`config.json` 位置仍按建议（同级优先，回退 Application Support）。

## 一、P0 — 开工前必须解决

### P0-1　Node.js 的 crypto 模块**没有 Argon2**

文档写的是「加密 = Node.js crypto，AES-256-GCM + Argon2id（scrypt 回退）」。问题在于：

- Node.js 内置 `crypto` **只有 `scrypt`，没有 argon2**（至今所有 LTS 版本都没有）。
- 所以「如不可用则回退到 scrypt」这句话，实际结果是 **100% 走到 scrypt**，Argon2id 永远用不上。安全说明里"有效抵抗 GPU 攻击"的承诺会落空。

**【需你决策】** 三选一：

| 方案 | 做法 | 代价 |
|---|---|---|
| A（推荐） | 引入 `hash-wasm` 的 argon2id（纯 WASM，无需原生编译，绿色版友好） | 性能约为原生的 30~50%，64MB 参数下预计 1~2 秒/次，需实测调参 |
| B | 引入 `argon2` 原生模块 | 需 electron-rebuild，Electron 22 + Win7 下 ABI 匹配容易翻车，跨平台打包麻烦 |
| C | 直接用内置 `scrypt`（N=2^15, r=8, p=1） | 零依赖最省事，抗 ASIC 弱于 Argon2id，但仍属可接受范围 |

我倾向 A。若选 A/C，`vault.meta` 的 `kdf` 字段必须如实写入实际使用的算法，不能写死 argon2id。

### P0-2　「全程不联网」与「检查更新」自相矛盾

- 手册 §1 说「全程本地运行，不联网，不上传任何文件」
- 手册 §8/§10 说「检查更新时连接更新服务器」
- 技术方案 §10 说「CSP 禁止联网」

对一个**安全产品**来说，这是信任层面的硬伤——用户一旦发现它会外联，会默认怀疑它还在偷偷干别的。而且 CSP 只约束渲染进程，主进程的 `fetch` 不受限制，所以技术上跑得通，但对外表述必须诚实。

**【需你决策】** 二选一：

1. **保留检查更新**，文案改为「除手动点击『检查更新』外，本软件不进行任何网络连接」，并在设置里做成默认关闭的开关；请求只能带 `platform` + `arch`，禁止带机器指纹、版本号以外的任何字段。
2. **彻底去掉联网能力**，改为在设置里放一个"前往官网查看最新版"的按钮（用 `shell.openExternal` 打开浏览器，仍由系统浏览器发起请求）。安全叙事最干净。

### P0-3　blob 格式缺少 AAD 绑定，存在密文搬运风险

当前 `ENC1` 结构里，`contentCiphertext` 只用 DEK 认证，没有把文件头/文件身份绑进去。后果：

- 攻击者（能接触 vault 目录的人，比如同步网盘）可以把 A 文件的密文段搬到 B 文件的 blob 里，解密时不报错。
- 配合 manifest 被替换，可以实现"用一个你能解的 blob 覆盖另一个文件"的定向攻击。

**建议改法（不破坏现有结构，只加字段）：**

```
content 段的 AAD = magic || version || wrappedDEK 三元组 || blobId
```

`blobId` 就是 manifest 里记录的那个 uuid。这样 blob 和它在目录树中的身份强绑定，跨文件搬运必然认证失败。

另外建议 manifest 里额外存一份 `contentTag`（或明文的 BLAKE3 摘要），做二次校验。

### P0-4　`vault.meta` 的 `verify` 字段结构不完整

文档写的是 `"verify": "base64..."`，但 AES-GCM 校验需要 **nonce + ciphertext + tag** 三元组，单个 base64 串放不下（除非自己拼，但那样容易写错）。

**建议改成结构化：**

```json
"verify": {
  "nonce": "base64...",
  "ciphertext": "base64...",
  "tag": "base64..."
}
```

同时注意：校验用的密钥要**从 masterKey 再 HKDF 派生一次**（`verifyKey ≠ masterKey`），不要把 masterKey 直接拿去加密已知明文，避免给攻击者提供"已知明文 + 密文"的分析材料。

### P0-5　~~macOS 把 `data/` 放在 `.app` 内部会出事~~　✅ 已决策并消解

文档 §3 和 §8.4 提到 `data/` 可能位于应用包内部。这里有雷：

- 往 `.app` 里写文件会破坏 ad-hoc 签名，可能触发 Gatekeeper 拦截（比"无法验证开发者"更难处理）；
- 如果 `.app` 在只读介质（DMG、光盘、部分 U 盘）上，直接写失败；
- 用户拖走 `.app` 时数据跟着走，但用户不知道，容易"丢"数据。

**建议：**

- 默认优先使用 **`.app` 同级目录** 的 `data/`（便携模式，符合 U 盘场景）；
- 若同级不可写，回退到 `~/Library/Application Support/YourApp/data/`；
- 首次启动时明确告诉用户"你的加密库在：`<路径>`"，并在设置里可查看/可迁移。

> **2026-09-11 更新：用户已决策「只支持选中文件库，不默认」。** 文件库位置由用户显式指定，不写入 `.app` 内部，上述风险点自然消解。仅 `config.json` 仍需遵循"同级优先、回退 Application Support"的规则。详见本文件顶部「已决策记录」。

## 二、P1 — 强烈建议调整

### P1-1　`ENC1` 没有预留分块字段，加视频要改格式

文档定的是整文件一次性 AES-GCM（单 nonce）。对 <50MB 没问题，但：

- 内存峰值 = 文件大小，1GB 文件在 Electron 里基本必崩；
- 之前需求确认时你选过"音视频都预览"，本版只列了音频。**【需你决策】** 视频到底要不要？

**建议：** 不管视频要不要，现在就在 `ENC1` 头部加两个保留字段（`chunkSize`、`flags`），保持向后兼容。真要做视频时不用改格式，不然到时全是存量数据迁移的麻烦。

### P1-2　「导入后原始明文不会被保留」有歧义

这句话容易被理解成"导入后原文件被销毁"，但实际实现大概是只加密入库、原文件不动。**【需你决策】**

建议明确为三选一：
1. 默认保留原文件（最安全，不会误删）；
2. 默认保留，提供「导入后删除原文件」开关；
3. 提供「安全擦除」选项——但要注明 **SSD / 云同步盘上覆写擦除不可靠**，别给用户虚假的安全感。

### P1-3　缺失几个刚需功能

工具栏只有「导入 / 导出 / 新建文件夹 / 锁定 / 设置」，实际用起来会缺：

- **删除**（必须，且要明确是否进回收站还是直接销毁——加密库里做回收站会长期留痕）
- **重命名**
- **修改主密码**（信封加密下成本极低，保险箱类工具的标配，缺了很奇怪）
- **搜索**（文件多了之后没有搜索基本不可用）

**【需你决策】** 第一版范围要不要包含这些。

### P1-4　主密码强度建议偏低

「建议 8 位以上，包含字母和数字」——8 位纯数字在 Argon2id 64MB 下也是分钟级可破的。

建议：改成「建议 12 位以上，或使用 4~5 个随机词组成的口令短语」，UI 加实时强度提示，弱密码允许但明确警告。

### P1-5　大文件走 IPC 传 ArrayBuffer 会卡

文档 §6.2 说「主进程解密后通过 IPC 传 ArrayBuffer 给渲染进程」。Electron IPC 走结构化克隆，几十 MB 的数据会有明显卡顿，且内存里同时存在两份拷贝。

**建议：** 阈值控制在 8~16MB 以内走 IPC；超过的走自定义协议（如 `vault://file/{id}`）流式返回，让 `<img>` / `<audio>` / `<video>` 直接消费流，不经过 JS 大对象。

### P1-6　manifest 整体重写没有原子性保护

「每次修改后整体重写 manifest.enc」——如果重写过程中崩溃/断电，整个目录树全丢，用户会失去所有文件的文件名（内容还在 blobs 里，但已经不知道谁是谁）。

**必须做：**
1. 写 `manifest.enc.tmp` → `fsync` → 原子 `rename` 覆盖；
2. 保留一份 `manifest.enc.bak`（上一版）；
3. 启动时若主文件校验失败，自动回退到 `.bak` 并提示用户。

这条不做，迟早出严重数据事故。

## 三、P2 — 需要你拍板的决策项

### P2-1　密钥文件 / U 盘双因子是否取消？

前一轮需求确认你选的是「主密码 + 密钥文件/U 盘」双因子，但本版文档的解锁方式只剩主密码。**【需你决策】** 是有意砍掉，还是文档漏写？

（个人意见：个人本地场景下砍掉是合理的，双因子最大的问题是"U 盘丢了 = 数据丢了"，对本产品定位弊大于利。）

### P2-2　OnlyOffice 的 AGPLv3 与体积问题

文档已经提到许可风险，补两点：

- **体积**：OnlyOffice WASM 资源包通常数百 MB，和手册里「500MB 磁盘空间」的最低要求直接冲突，得把最低要求改到 1.5GB 左右。
- **闭源分发**：AGPLv3 要求衍生作品同样开源。若本软件闭源对外销售，必须购买商业授权，费用不低。

**【需你决策】** 是接受 AGPL 开源、买商业授权、还是换方案（LibreOffice 无头转 PDF / 只做 PDF 预览 + Office 走导出外部打开）。

### P2-3　Electron 22 已 EOL，安全产品用 EOL 内核是硬伤

Electron 22 对应 Chromium 108，2023 年初已停止维护，存在未修复的 CVE。一个主打"安全"的产品跑在有已知漏洞的浏览器内核上，被懂行的人指出来会很尴尬。

**【需你决策】** 二选一：
- 保 Win7 → 锁 Electron 22，在产品说明里明确告知风险；
- 保安全 → 放弃 Win7，用当前 Electron LTS（Win7 市场份额已极低）。

我倾向后者。另外注意：Electron 22 只能在 **macOS 主机** 上打出 universal 包，这点要在构建环境里提前规划。

### P2-4　blob 文件名用 UUID 的注意点

用 UUIDv4 没问题，但别用 v1（含 MAC 地址和时间戳，会泄露机器信息）。

## 四、已确认无需变更的部分

以下设计与我此前的建议一致，直接沿用即可：

- 信封加密（每文件独立 DEK + masterKey 包装）—— 改密码不重加密全文，正确
- manifest 整体加密而非文件名逐个确定性加密 —— 更简单且泄露面更小，正确
- 明文不落盘、Blob URL 用完 revoke
- 锁屏即 `Buffer.fill(0)` 清空 masterKey
- `contextIsolation` / `nodeIntegration:false` / `sandbox:true` / preload 最小 API
- 绿色版不走 electron-updater，改手动更新 + data 目录迁移
- 监听 `suspend` / `lock-screen` 自动锁定

### 7.1 能力探测三项 —— 全部通过

在 **Node v24.21.0 win-x64** 实测（项目最低要求 Node 24.7，Electron 43 内置 24.17，满足）：

| 探测项 | 结果 |
|---|---|
| `crypto.argon2Sync` 是否存在 | ✅ 存在 |
| 是否需要 `--experimental-argon2` | ❌ 不需要（传该标志反而报 `bad option`） |
| 64MB / 3 passes 耗时 | ✅ **231ms**（1 pass 89ms，2 passes 164ms），落在 100–500ms 区间 |

**额外发现两个会直接导致线上事故的坑：**

1. `argon2Sync` 的真实签名是 `(algorithm, parameters)`，字段名是
   `message` / `nonce` / `memory` / `passes` / `parallelism` / `tagLength`
   —— 不是直觉上的 `password` / `salt` / `memoryCost` / `timeCost` / `hashLength`，
   且六个字段全部必填。照抄网上写法必然报错，且报错信息具有误导性。
   已写入基线 §5.1 并保留探测脚本 `scripts/probe-argon2.mjs`。
2. scrypt 兜底参数 `N=2^15, r=8` 需要 128·N·r = 32MiB，**超过 Node 默认 maxmem**，
   不显式设置 `maxmem` 会直接抛 `ERR_CRYPTO_INVALID_SCRYPT_PARAMS`。基线已修正。
