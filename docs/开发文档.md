# 一、用户手册与功能介绍

## 1. 软件简介

本软件是一款本地离线、绿色免安装的加密文件管理工具。

打开软件后先**选择或新建一个文件库**，再输入主密码，即可解锁整个加密库。

支持手动导入导出，也支持直接剪切加密库文件夹迁移到另一台电脑，在新电脑上"打开文件库"选中它即可继续使用。

密码正确可查看所有目录和文件，密码错误则无法显示任何内容。

支持预览 Word、Excel、PPT、PDF、TXT、Markdown、图片、音频等常见格式。

支持自动锁屏，超时后需重新输入主密码。

全程本地运行，不联网，不上传任何文件。

## 2. 系统要求

| 平台 | 最低要求 |
|---|---|
| Windows 10 / 11（x64、ARM64） | 4GB 内存，2GB 磁盘空间 |
| macOS 13 (Ventura) 及以上（Intel / Apple Silicon） | 4GB 内存，2GB 磁盘空间 |

> **不再支持 Windows 7 / 8 / 8.1。** 其最后一个可用版本 Electron 22 已于 2023 年停止维护，Chromium 108 存在未修复的安全漏洞。作为安全类软件，不能运行在已停止安全更新的内核上。
>
> macOS 版本要求由 Electron 43 决定（官方 README 标注 Ventura 及以上；Electron 42 为 Monterey）。**立项第一步需用实际构建包验证最低可运行的 macOS 版本。**
>
> 磁盘空间从 500MB 上调到 2GB，主要因为内置了 OnlyOffice WASM 预览资源包（已裁剪）。

## 3. 安装与启动

### 绿色免安装说明

本软件不制作安装程序，发布为 ZIP 压缩包，解压即用。不写注册表、不创建开始菜单、不依赖系统服务。

### Windows

1. 下载 `宝宝巴士-green-win-x64.zip`。
2. 解压到任意可写目录（建议非 Program Files，如桌面或 D 盘）。
3. 双击 `宝宝巴士.exe` 启动。
4. 首次运行进入**文件库选择界面**，需自行新建或选择一个文件库目录（详见第 4 节）。软件不会自动创建任何文件库。

### macOS

1. 下载 `宝宝巴士-green-macos-universal.zip`（同时支持 Intel 和 Apple Silicon 芯片）。
2. 解压后得到 `宝宝巴士.app`，拖入"应用程序"文件夹或保留在任意目录。
3. 首次打开时，macOS 可能提示"无法验证开发者"。在"系统设置 → 隐私与安全性"中点击"仍要打开"，或右键点击应用选择"打开"。
4. 首次运行进入**文件库选择界面**，需自行新建或选择一个文件库目录（详见第 4 节）。软件不会自动创建任何文件库。

说明：macOS 通用二进制包含 x64 和 arm64 两种架构，一个应用即可在 Intel Mac 和 Apple Silicon Mac 上运行。

## 4. 首次使用

**本软件不预设、不自动创建任何文件库。文件库的位置完全由你指定**——可以放在本机任意目录，也可以直接放在 U 盘、移动硬盘或网盘同步文件夹中。

启动后进入文件库选择界面，有两条路径：

### 路径一：新建文件库

1. 点击「新建文件库」。
2. 在系统弹出的目录选择窗口中，选择一个**用于存放文件库的文件夹**（例如 `D:\我的保险箱` 或 U 盘根目录）。
   - 建议选择一个空文件夹；若文件夹非空，软件会在其中创建 vault 结构，不会改动已有的其他文件。
3. 输入主密码。**必须满足：长度 8 位以上，且同时包含字母和数字**（不满足时软件拒绝创建，不会放行）。
4. 再次输入确认。
5. 软件在该目录下生成 `vault.meta`、`manifest.enc`、`blobs/`。
6. 进入主界面，可以开始导入文件。

### 路径二：打开已有文件库

1. 点击「打开文件库」。
2. 选中已有的文件库文件夹（即包含 `vault.meta` 的那一层目录）。
3. 输入该库的主密码。
4. 密码正确进入主界面；密码错误则无法显示任何内容。

> **重要提示：主密码一旦忘记无法找回，请务必牢记或备份到安全位置。**
>
> **提示：文件库就是那个你亲手选中的文件夹本身。它自包含、可整体复制迁移，请自己记住它在哪里——软件不会替你猜测位置。**

## 6. 核心功能操作

### 6.1 导入文件（加密入库）

**方式一：拖拽导入**

- 从系统资源管理器拖入文件到软件窗口 → 导入到根目录。
- 拖到左侧某个文件夹节点 → 导入到该文件夹下。
- 拖入文件夹 → 递归导入所有支持的文件。
- 支持一次拖入多个文件。

**方式二：按钮导入**

1. 点击顶部"导入"按钮。
2. 选择文件或文件夹。
3. 文件自动加密入库，原始明文不会被保留。

导入后的文件使用 AES-256 加密存储，原始文件名和内容全部加密保护。

> **关于原始文件：默认原样保留，不删除、不改动。** 本软件不会替你销毁原始明文文件——删除是不可逆操作，交由你自己决定更安全。需要清理时，请在导入完成后自行删除原文件，并注意：
> - 普通删除只是移除索引，数据仍留在磁盘上，可用恢复软件找回；
> - 在 SSD、U 盘、以及各类网盘同步目录上，"覆写擦除"并不保证真正生效（磨损均衡与快照机制），不要依赖它；
> - 若确实需要彻底销毁，建议使用全盘加密（BitLocker / FileVault）后删除密钥，而不是依赖文件级擦除。

### 6.2 查看文件

点击左侧文件树中的任意文件，右侧自动显示文件内容。

支持预览的格式：

| 类型 | 支持格式 |
|---|---|
| 文档 | DOCX、XLSX、PPTX、PDF、TXT、Markdown、HTML、ODT、ODS、ODP 等 |
| 图片 | JPG、PNG、GIF、BMP、WebP 等 |
| 音频 | MP3、WAV、AAC、FLAC 等 |

Markdown 文件以渲染后的格式显示，TXT 文件以纯文本显示。图片和音频直接在预览区域播放，无需外部播放器。

### 6.3 导出文件（解密为普通文件）

1. 选中文件或文件夹。
2. 点击顶部"导出"按钮。
3. 选择导出目录。
4. 软件解密并写出普通 Office 文件，可被 WPS、Microsoft Office 等软件直接打开。

注意：导出后的文件不再受本软件保护，请自行注意安全。

### 6.4 文件树内部拖拽

在左侧文件树中拖动文件或文件夹，可以调整分类位置。拖到目标文件夹上松开即可完成移动。

### 6.5 自动锁屏

- 软件闲置超过设定时间后自动锁屏。
- 锁屏后需重新输入主密码才能继续使用。
- 可在"设置"中调整自动锁屏时间：1 分钟 / 5 分钟 / 15 分钟 / 30 分钟 / 1 小时 / 从不。
- 系统休眠或睡眠时自动锁定。
- 也可手动点击顶部"锁定"按钮立即锁定。

### 6.6 文件库管理

软件同时只能打开一个文件库。所有文件库操作都通过顶部「文件库」按钮进入。

| 操作 | 说明 |
|---|---|
| 新建文件库 | 选择一个文件夹作为新的文件库，设置主密码后初始化 |
| 打开文件库 | 选中已有的文件库文件夹，输入主密码解锁 |
| 切换文件库 | 先锁定当前库，再打开另一个库 |
| 从列表移除 | 仅把某条记录从"最近使用"列表中删掉，**不会删除磁盘上的任何数据** |

关于"最近使用的文件库"：

- 软件会记录你打开过的文件库路径，方便下次快速进入。
- 该记录只保存在本机配置文件中（路径 + 你为它起的别名 + 最后打开时间），**不含密码、密钥和任何文件内容**。
- 可以在设置中关闭"记住最近的文件库"。关闭后，每次启动都必须手动选择文件库位置。
- **注意：这只是快捷方式，不是数据。** 文件库本身始终是一个普通的磁盘文件夹，不依赖本软件也能被复制、备份、迁移。

> 若"最近列表"里的某个文件库打不开（U 盘没插、文件夹被移动或删除），软件会提示"未找到文件库"，此时应点击「打开文件库」重新指定位置，**不要**选择"新建文件库"——在同一个文件夹上再次新建会覆盖原有的 `vault.meta`，导致原数据永久无法解密。

### 6.7 重命名与删除

**重命名：** 选中文件树中的节点，右键选择「重命名」，或按 `F2`。改名只影响 `manifest.enc` 中的记录，不动 blob 内容，瞬时完成。

**删除：** 选中后右键选择「删除」，或按 `Delete`，二次确认后移除。

删除的默认行为是**直接销毁，不进回收站**：

- 该文件的 blob 文件被删除，对应的 DEK 随之消失，数据不可恢复；
- 目录树记录从 `manifest.enc` 中移除；
- **这是刻意设计**——如果在加密库里做"回收站"，已删除的敏感文件会继续以密文形式长期留存，等于没删。

> 删除是**不可恢复**的操作，请确认无误再执行。

### 6.8 搜索

在左上角搜索框输入关键词，实时过滤当前文件库中的**文件名**（不含文件内容）。

- 搜索在已解密的 `manifest` 上做，纯内存操作，不产生任何明文落盘；
- 匹配范围为文件名，不区分子目录层级；
- **不支持全文检索**。原因是：文件内容全部是密文，要做全文检索必须维护一份明文索引，而索引本身会成为新的泄密面——这与本产品的安全定位冲突。如果你需要全文检索能力，请另行评估可搜索加密（SSE）方案，那会显著改变整体架构。

### 6.9 修改主密码

在「设置」中点击「修改主密码」，依次输入当前密码和新密码即可。

- 由于采用信封加密（每个文件的 DEK 由主密钥包装），改密码**只需要重新包装各文件的 DEK**，不需要重新加密任何文件内容，几千个文件也能在几秒内完成；
- 改密码会重新生成 KDF 盐值；
- 新密码同样必须满足"8 位以上且包含字母和数字"；
- 改密码过程中断（崩溃、断电）可能导致部分 DEK 已用新密钥包装、部分仍是旧的。实现上采用"先写临时 manifest → 原子替换"的方式，保证要么全部完成、要么全部回滚，**不会出现半改状态**。

## 7. 迁移加密库

本软件的文件库是自包含的，可以整体迁移到另一台电脑或移动介质。

**因为文件库位置由用户自己指定，迁移时不需要把文件放到软件目录下的任何固定位置。**

步骤：

1. 关闭软件（或先点击「锁定」）。
2. 找到你当初指定的那个文件库文件夹（里面包含 `vault.meta`、`manifest.enc`、`blobs/`）。
3. 复制或剪切整个文件夹到目标位置（另一台电脑、U 盘、移动硬盘、网盘同步目录均可）。
4. 打开软件，点击「打开文件库」，选中迁移后的文件夹。
5. 输入主密码：
   - 密码正确：目录和文件全部显示，可以正常使用。
   - 密码错误：目录和文件全部不显示，无法查看任何内容。

文件库包含了所有加密数据和加密的目录结构，不依赖原电脑的任何本地状态。

**放到网盘同步目录的说明：** 文件库由大量小文件组成，网盘同步本身是安全的（同步的是密文），但要注意——如果在两台电脑上同时打开同一个库并各自修改，同步冲突可能导致 `manifest.enc` 被覆盖而丢失目录结构。建议同一时间只在一台设备上使用。

## 8. 软件更新

本软件支持以下更新方式：

**方式一：手动更新（推荐）**

1. 从官方网站或指定渠道下载最新版本的 ZIP 压缩包。
2. 解压到新的目录（旧版本可以先留着，确认无误后再删除）。
3. 启动新版本，点击「打开文件库」，选中你原来的文件库文件夹即可。
4. **不需要复制任何数据**——文件库本来就在你自己指定的位置，新旧版本读的是同一个文件夹。

> 由于文件库不在软件目录内，更新软件只需替换程序本身，数据与程序完全解耦，误删程序目录也不会影响加密数据。

**方式二：前往官网查看（本软件自身不联网）**

1. 打开软件，在"设置"中点击「前往官网查看更新」。
2. 软件调用**系统默认浏览器**打开官网发布页。请求由浏览器发起，本程序自身不产生任何网络流量。
3. 自行下载新版 ZIP，按方式一替换即可。

> 本软件**不具备任何网络能力**——没有更新检测接口，没有版本上报，没有崩溃上报，没有埋点。
>
> 这不是技术限制，而是刻意取舍：一个加密软件只要保留一条联网通道，用户就无法验证它到底传了什么。去掉全部网络能力，是"不联网"这个承诺能被真正兑现的唯一方式。代价是用户需要手动检查更新，我们认为这个代价值得。

更新不会影响加密库数据。文件库格式在新旧版本之间保持兼容，更新后「打开文件库」选中原位置即可继续使用。

## 9. 安全说明

### 加密机制

- 使用 AES-256-GCM 加密文件内容，这是当前国际公认的安全加密标准。
- 主密码通过 Argon2id 算法派生加密密钥（如不可用则回退到 scrypt），有效抵抗暴力破解和 GPU 攻击。
- 每个文件使用独立的随机密钥加密，文件密钥再用主密钥包装，即使单个文件的密钥泄露也不会影响其他文件。
- 文件名和目录结构同样加密存储，密码错误时无法获取任何文件信息。

### 安全行为

- 解密仅在内存中进行，绝不将明文写入磁盘临时文件。
- 锁屏后立即清空内存中的密钥和解密数据。
- 软件不联网、不上传任何文件。
- 日志不记录密码、密钥和文件内容。
- 配置文件只记录文件库路径和你的界面偏好，不含密码、密钥和文件内容；可在设置中关闭"记住最近的文件库"。
- 导出的文件不再受保护，请用户自行注意。

### 密码安全建议

- **必须** 8 位以上，且同时包含字母和数字（软件强制校验，不满足无法创建文件库）。
- 更推荐使用 4~5 个随机词组成的口令短语（如「蓝色-台灯-香蕉-92」），比同等长度的乱码更好记也更难破解。
- 不要使用生日、电话号码等容易猜到的密码。
- 不要将密码写在便签上贴在电脑旁。
- 忘记密码无法恢复，请务必牢记。

## 10. 常见问题

**Q：忘记主密码怎么办？**
A：无法找回。这是加密软件的安全设计。建议首次设置时记录在安全的地方。

**Q：加密库可以放到 U 盘上吗？**
A：可以。新建文件库时直接选择 U 盘上的文件夹即可，加密库随 U 盘携带。软件本体也可以整个放在 U 盘上运行，程序和数据可以分别放在不同位置。

**Q：文件库在哪个文件夹？我忘记了。**
A：软件不预设位置，文件库就是你当初自己选中的那个文件夹。可以在状态栏左侧或「文件库 → 最近使用」中查看当前库的路径；如果记录已清空，需要用系统搜索查找包含 `vault.meta` 的文件夹。

**Q：可以同时在多台电脑上打开同一个文件库吗？**
A：技术上可以（比如放在网盘同步目录里），但不建议同时打开并各自修改——同步冲突可能覆盖 `manifest.enc` 导致目录结构损坏。建议同一时间只在一台设备上使用。

**Q：软件需要联网吗？**
A：**完全不需要，而且它根本没有联网能力。** 程序内不包含任何网络请求代码：不检测更新、不上报崩溃、不发送任何统计数据。需要查看新版本时，可点击「前往官网查看更新」，由系统浏览器打开网页——这一步的网络请求来自浏览器，与本软件无关。

**Q：导出的文件安全性如何？**
A：导出后解密为普通文件，不受本软件保护。请确认导出目标位置的安全。

**Q：支持哪些文件格式预览？**
A：支持 Office 文档（Word/Excel/PPT）、PDF、TXT、Markdown、图片和音频。其他格式可以加密存储和导出，但不支持预览。

**Q：macOS 上提示"无法验证开发者"怎么办？**
A：在"系统设置 → 隐私与安全性"中点击"仍要打开"，或右键点击应用选择"打开"。

**Q：软件更新会丢失数据吗？**
A：不会。文件库本来就在你自己指定的位置，不在软件目录内。更新后启动新版，点击「打开文件库」选中原文件夹即可，无需复制任何数据。

## 4. 自包含加密库设计

**文件库根目录 = 用户在新建/打开时显式选择的那个文件夹。软件不设默认库、不自动建库。**

由此带来几条硬约束：

1. 启动时若 `rememberRecentVaults` 为 false 或历史记录为空，直接进入文件库选择界面。
2. 历史记录中的路径失效（U 盘拔出、文件夹被移动/重命名/删除）时，提示"未找到文件库"并提供「重新选择位置」，**绝不静默新建**。
3. 新建文件库前必须校验目标文件夹是否已是文件库（存在 `vault.meta`）；若是，强制改为"打开"流程，防止覆盖导致数据永久丢失。
4. 打开文件库时必须校验 `vault.meta` 的 `version` 字段，不兼容则拒绝打开并提示升级，不改写原文件。

### 4.0 vault 定位与校验流程

```
启动
 ├─ 有历史记录且路径有效 → 直接进密码界面（显示库名/别名）
 ├─ 有历史记录但路径失效 → 提示"未找到" → 重新选择位置 / 从列表移除
 └─ 无历史记录          → 文件库选择界面
                          ├─ 新建文件库 → 选目录 → 校验非库 → 设密码 → 初始化
                          └─ 打开文件库 → 选目录 → 校验 vault.meta → 输密码
```

### 4.1 vault.meta（非敏感）

```json
{
  "version": 3,
  "kdf": "argon2id",
  "kdfImpl": "node-crypto",
  "kdfParams": {
    "memoryCost": 65536,
    "timeCost": 3,
    "parallelism": 1,
    "hashLength": 32
  },
  "salt": "base64...",
  "verify": {
    "nonce": "base64...",
    "ciphertext": "base64...",
    "tag": "base64..."
  }
}
```

- `kdf`：**Argon2id 优先**，使用 Node.js 内置 `crypto.argon2Sync`（Node 24.7 起提供，Electron 43 内置 Node 24.17，满足要求）。若运行时探测到不可用，回退 `scrypt`（N=2^15, r=8, p=1），并把实际使用的算法如实写入 `kdf` 字段，**不允许写死 argon2id**。
- `kdfImpl`：记录实现来源（`node-crypto` / `scrypt` / `hash-wasm`），便于日后排查兼容问题。
- `salt`：16 字节随机值。
- `verify`：密码正确性校验值。必须从 masterKey **再派生一次独立密钥**后生成，避免用 masterKey 直接加密已知明文：

  ```
  verifyKey = HKDF-SHA256(masterKey, salt, info = "vault-verify-v1", len = 32)
  verify    = AES-256-GCM(verifyKey, nonce, plaintext = "unlock-check")
  ```

  存 `nonce` / `ciphertext` / `tag` 三元组，**不能用单个 base64 串**（GCM 需要三元组才能校验）。
- 不含任何文件名、目录结构等敏感信息。
- 文件整体可迁移，不依赖原电脑本地状态。

### 4.2 manifest.enc（加密的目录树）

解密后是一个 JSON：

```json
{
  "version": 2,
  "nodes": [
    {
      "id": "uuid-1",
      "parentId": null,
      "type": "folder",
      "name": "项目资料",
      "createdAt": 1700000000,
      "updatedAt": 1700000000
    },
    {
      "id": "uuid-2",
      "parentId": "uuid-1",
      "type": "file",
      "name": "合同.docx",
      "ext": "docx",
      "size": 123456,
      "blob": "blobs/uuid-2.enc",
      "createdAt": 1700000000,
      "updatedAt": 1700000000
    }
  ]
}
```

加密方式：

- 使用 masterKey 经 HKDF 派生独立的 manifestKey（`info = "vault-manifest-v1"`），不直接用 masterKey。
- 整体 AES-256-GCM 加密，一次性读写（目录树 JSON 通常只有几 KB~几 MB）。
- 每次修改后整体重写 manifest.enc。

**写入必须原子化（P1-6，否则崩溃即丢整个目录树）：**

```
1. 序列化 + 加密到内存
2. 写入 manifest.enc.tmp 并 fsync
3. 把当前 manifest.enc 另存为 manifest.enc.bak   // 必须在 rename 之前！
4. rename(manifest.enc.tmp → manifest.enc)       // 原子替换
5. fsync(目录)                                    // Windows 不支持，尽力而为
```

> **顺序更正（M0 实现时发现）：** 原文档把"备份 .bak"写在 rename 之后，这在物理上不可能 —— rename 之后旧文件已经不存在了，没有东西可备份。正确顺序是**先备份，再 rename**。实现见 `src/main/crypto/manifest.ts`。
>
> 另外，主文件与备份**都**解密失败时，必须抛出人能看懂的中文提示，而不是把 GCM 底层的
> `Unsupported state or unable to authenticate data` 直接丢给用户。

启动时若 `manifest.enc` 的 GCM 校验失败，自动回退加载 `manifest.enc.bak` 并提示用户"已从上一次备份恢复，最近的部分改动可能丢失"。

> 不做这一步，一次断电就足以让用户失去**所有文件的文件名**——内容还在 blobs 里，但已经不知道谁是谁。这是本项目的头号数据事故风险。

manifest 中每个文件节点额外记录 `blobId` 与 `contentTag`，与 §4.3 的 AAD 绑定和二次校验配套。

### 4.3 blobs（加密的文件内容）

每个文件独立加密，使用信封加密。文件名为 `{uuid}.enc`，**uuid 必须使用 UUIDv4**（随机），禁止使用 UUIDv1——v1 内嵌 MAC 地址和时间戳，会泄露机器信息与文件创建时间。

### blob 二进制结构（ENC1 / version 2）

```
┌─ Header（明文，38 字节）─────────────────────────────┐
│ magic         4B    "ENC1"                          │
│ version       1B    2                               │
│ flags         1B    bit0: 1=分块模式 / 0=整文件模式   │
│ chunkSize     4B    分块大小（BE），整文件模式填 0     │
│ chunkCount    4B    块数量（BE），整文件模式填 0       │
│ blobId        16B   UUIDv4 原始字节                  │
│ plainSize     8B    明文字节数（BE）                  │
├─ wrappedDEK 段 ─────────────────────────────────────┤
│ wrappedDEKNonce       12B                           │
│ wrappedDEKTag         16B                           │
│ wrappedDEKCiphertext  32B                           │
├─ content 段 ────────────────────────────────────────┤
│ contentNonce          12B                           │
│ contentTag            16B                           │
│ contentCiphertext     变长                           │
└─────────────────────────────────────────────────────┘
```

`chunkSize` / `chunkCount` 是**为将来分块模式预留的字段**，当前版本固定写 0（整文件模式）。真要做视频/超大文件时把 `flags` 的 bit0 置 1、`version` 升到 3 即可，**不需要迁移存量文件**（按 version 分支处理）。

### AAD 绑定（P0-3 修复，必须有）

不加 AAD 的话，攻击者可以把 A 文件的密文段搬到 B 文件的 blob 里而不被发现。因此两段加密都必须绑定上下文：

```
AAD(wrappedDEK) = Header 全部 38 字节
AAD(content)    = Header 全部 38 字节
```

并且 **`blobId` 必须等于 manifest 中该节点的 `id`**。这样 blob 与它在目录树中的身份强绑定：跨文件搬运、替换、截断都会导致 GCM 认证失败。

> **AAD(content) 的更正（M0 实现时发现基线内部矛盾）：**
>
> 原方案写的是 `AAD(content) = AAD(wrappedDEK) || wrappedDEK 三段`，但这与 §5.3 承诺的
> "改主密码时只需重新包装 DEK，不需要重新加密所有文件内容"**直接冲突** —— 重包装 DEK 会改变
> wrappedDEK 的字节，content 的 AAD 随之失效，于是改一次密码必须把整个库重新加密一遍。
>
> 而并上 wrappedDEK 段换来的额外保护实际为零：
> - 跨文件搬运已经被 Header 里的 `blobId` 阻断（A 的 content 搬到 B，会用 B 的 DEK 和 B 的 Header 去解密，认证必然失败）；
> - "替换同一 blob 内的 wrappedDEK 段"要成立，攻击者必须能用 masterKey 包装一个他自己知道的 DEK —— 那意味着 masterKey 已经泄露，防护早已失去意义。
>
> 因此改为**两段都只绑 Header**，保住改密码 O(文件数) 的性能承诺；
> "文件被整体替换"的兜底交给 manifest 里记录的 `contentTag`。
> 单元测试 `tests/blob.spec.ts` 覆盖了这几种搬运场景。

### 各字段说明

- DEK：随机 32 字节文件密钥（每次写入文件时新生成，不复用）。
- wrappedDEK：用 masterKey 包装的 DEK；校验失败即视为密码错误或数据被篡改。
- content：用 DEK + AES-256-GCM 加密的明文内容。
- `plainSize` 参与 AAD，防止密文被截断后仍通过校验。
- manifest 中额外记录 `contentTag`，作为第二重校验。
  **实现为整个 blob 的 SHA-256**，而非原文档写的 BLAKE3-256 —— Node 内置 `crypto` 没有 BLAKE3，
  为一个摘要再引入一个第三方依赖不值得；这里的用途是"检测文件被整体替换"，SHA-256 完全够用。

## 5. 加密安全方案

### 5.1 密钥派生（KDF）

| 算法 | 优先级 | 实现 | 参数 |
|---|---|---|---|
| Argon2id | 首选 | Node.js 内置 `crypto.argon2Sync` | 内存 64MB，迭代 3 次，并行度 1，输出 32 字节 |
| Argon2id | **次选（Electron 下的实际路径）** | `hash-wasm` WASM 实现 | 同上，逐字节兼容内置实现 |
| scrypt | 末选兜底 | Node.js 内置 `crypto.scryptSync` | N=2^15，r=8，p=1，**且必须显式设置 `maxmem` ≥ 64MB** |

Argon2id 是密码哈希竞赛（PHC）的获胜者，提供对 GPU 和 ASIC 攻击的强抵抗力，同时具备侧信道攻击防护能力。目标是在生产硬件上每次派生耗时 100–500ms。

---

#### ⚠️ 重大更正：Electron 里 Node 内置 Argon2 **不可用**（M1 实测，2026-09-11）

M0 阶段曾根据"Electron 43 内置 Node 24.17 > 24.7 门槛"推断内置 Argon2id 可用，**该结论错误**。
在真实 Electron 43.7.0 中实测：

```
[env] Electron 43.7.0 / Node 24.21.0 / Chromium 150.0.7871.250
[kdf] node argon2id   : 不可用（Argon2 algorithm not supported）
[kdf] wasm argon2id   : 448~491ms  ✅
[kdf] scrypt          : 314~327ms
[kdf] pbkdf2-sha512   : 594~860ms
```

**根因：Electron 链接的是 BoringSSL（Chromium 系），不是 OpenSSL。**
Node 的 `crypto.argon2Sync` 依赖 OpenSSL 3.5+ 提供的 Argon2 KDF，BoringSSL 没有实现，
于是 `typeof crypto.argon2Sync === 'function'` 成立，但**一调用就抛
`ERR_CRYPTO_ARGON2_NOT_SUPPORTED`**。

这条教训比结论本身更重要：**能力探测必须实跑一次，只判断 API 存在性会被坑。**
（`scrypt` 和 `pbkdf2` 在 Electron 下正常，因为它们由 Node 自身实现，不依赖 OpenSSL 新特性。）

**最终方案：三级降级链**

```
Node 内置 argon2id（236ms）  →  hash-wasm argon2id（430ms）  →  scrypt（327ms）
```

启动首次派生时用 8MB/1pass 小参数实跑探测，结果缓存在进程内，避免每次都付 400ms。

**跨实现兼容性已验证**（`scripts/verify-kdf-compat.mjs`）：
hash-wasm 与 Node 内置在相同参数下**输出逐字节一致**，
因此 `vault.meta` 只需记录 `kdf: "argon2id"` + 参数，**不必绑定具体实现** ——
换机器、换实现都能打开同一个库。

| 探测项 | 结果 |
|---|---|
| 内置 API 是否存在 | ✅ 存在（但调用即失败，见上） |
| 内置 Argon2id 在 Electron 中 | ❌ `ERR_CRYPTO_ARGON2_NOT_SUPPORTED` |
| hash-wasm Argon2id 在 Electron 中 | ✅ 448~491ms（64MB / 3 passes）|
| 两种实现输出一致性 | ✅ 逐字节相同 |
| Node 内置实现符合 RFC 9106 | ✅（字段名是 `associatedData`，不是 `ad`）|
| scrypt 未设 maxmem | ❌ 抛 `ERR_CRYPTO_INVALID_SCRYPT_PARAMS`，**必须显式给 maxmem** |

**⚠️ 真实签名与字段名（与常见直觉完全不同，照抄网上的写法必然报错）：**

```javascript
// 不是 argon2Sync(password, salt, options)！
const key = crypto.argon2Sync('argon2id', {
  message:     passwordBuffer,   // 注意：不叫 password
  nonce:       saltBuffer,       // 注意：不叫 salt（Argon2 语境下盐就叫 nonce）
  memory:      65536,            // 单位 KiB；不叫 memoryCost
  passes:      3,                // 不叫 timeCost / iterations
  parallelism: 1,
  tagLength:   32,               // 输出字节数；不叫 hashLength
});
```

六个字段**全部必填、没有默认值**，任一缺失都会抛 `ERR_INVALID_ARG_TYPE`。
字段名写错不会提示"不支持"，而是报"该字段为 undefined"，极易被误判成运行时不支持 Argon2
—— 因此探测脚本 `scripts/probe-argon2.mjs` 必须实跑一次，而不能只判断 `typeof`。

**hash-wasm 的参数名映射**（与 Node 内置不同，别写混）：

```javascript
await argon2id({
  password,
  salt,
  memorySize:   65536,   // 对应 Node 的 memory（KiB）
  iterations:   3,       // 对应 Node 的 passes
  parallelism:  1,
  hashLength:   32,      // 对应 Node 的 tagLength
  outputType: 'binary',
})
```

`hash-wasm` 只提供**异步** API，因此整条派生链路（`deriveMasterKey` →
`createVaultMeta` / `verifyPassword` → `Vault.create` / `Vault.open` / `changePassword`）
都必须是 `async`。这是 M1 对 M0 代码结构最主要的一处改动。

三级降级链全部失败时才回退 scrypt，并在 `vault.meta` 中如实写 `kdf: "scrypt"`。

> 派生过程应放在**主进程**执行，并让 UI 显示"正在派生密钥…"。64MB 内存占用 + 数百毫秒耗时下，直接在渲染线程跑会卡住界面。

### 5.2 对称加密

- 算法：AES-256-GCM（认证加密）
- Nonce：96 位随机值，**每次加密独立生成，绝不复用**
- 认证标签：128 位
- AAD：按 §4.3 绑定文件头与 blobId，**不允许留空**
- 不使用 CBC、ECB、CTR 等非认证模式

> **GCM nonce 复用是本方案里最致命的误用**：同一个密钥下复用一次 nonce，攻击者就能恢复出认证子密钥，进而伪造任意密文，等于整层加密失效。
>
> 因此规则是硬性的：**每次写入都用全新随机 nonce**。文件被修改后重新加密时必须换新 nonce（不能沿用旧文件的），DEK 也同时重新生成。
>
> 另外，单个密钥加密的数据量存在上限（约 2^39-256 bit ≈ 64GB），本项目单文件控制在 100MB 量级，远低于上限，安全。

### 5.3 信封加密

每个文件使用独立的随机 DEK（数据加密密钥），DEK 用 masterKey 包装。这样设计的好处：

- **隔离性**：单个文件的 DEK 泄露不影响其他文件。
- **性能**：修改主密码时只需重新包装 DEK，不需要重新加密所有文件内容。
- **灵活性**：可以支持不同的加密参数而不影响已有文件。

### 5.4 内存安全

- masterKey 仅保存在主进程内存中，渲染进程无法直接访问。
- 锁屏或关闭预览时，立即清空内存中的解密数据和 Buffer。
- 使用 `Buffer.fill(0)` 覆写敏感内存。

## 6. 多格式预览方案

预览功能分为两条技术路线：

### 6.1 Office 文档预览（OnlyOffice WASM）

适用于：DOCX、XLSX、PPTX、PDF、ODT、ODS、ODP 等。

- 将 OnlyOffice WASM 资源放在 `resources/onlyoffice-wasm/`。
- 渲染进程通过自定义协议加载（**不用 `file://`**，见 §10）。
- 主进程解密文件内容后，小文件经 IPC 传 ArrayBuffer、大文件经 `vault://` 流式供给（见 §6.3）。
- 渲染进程生成 Blob，交给 WASM 引擎渲染。

**资源包必须裁剪（P2-2 决策）。** 官方完整包数百 MB，其中大量内容对本产品无用。裁剪方向：

| 内容 | 处理 |
|---|---|
| 编辑器完整 UI（工具栏、菜单、公式编辑器等） | 剔除，只保留只读渲染所需模块 |
| 示例文档、帮助文件、多语言包（保留中英两种） | 剔除 |
| 字体子集（保留中文字体的常用子集） | 大幅裁剪，这是体积大头 |
| 若采用 pi-view-port 一类社区统一预览层 | 按其精简版构建，避免引入完整编辑器 |

裁剪后目标控制在 **300~500MB** 以内，并把手册中的磁盘要求同步调整为 2GB。

> **AGPLv3 仍需注意：** OnlyOffice 采用 AGPLv3 许可。若本软件闭源对外分发，需要购买商业授权。裁剪资源包不改变许可约束。若日后不打算开源也不打算买授权，备选路线是 LibreOffice 无头模式转 PDF 后走 PDF 通道预览（体积同样不小，但许可更宽松）。

配置只读模式：

```javascript
editorConfig: {
  mode: 'view',
  customization: {
    compactHeader: true,
    hideRightMenu: true,
    waterMark: {
      value: '当前用户\n时间',
      opacity: 0.25
    }
  }
}
```

关闭预览时销毁 Blob 和 WASM 实例。

OnlyOffice 支持 Markdown、TXT 等格式的预览和转换。

### 6.2 其他格式预览（自研渲染层）

| 格式 | 预览方式 |
|---|---|
| TXT | 渲染进程直接以 `<pre>` 或 `<textarea readonly>` 显示 |
| Markdown | 使用 marked 或 markdown-it 渲染为 HTML |
| 图片 | 解密后生成 Blob URL，`<img>` 标签展示 |
| 音频 | 解密后生成 Blob URL，`<audio controls>` 播放 |

统一处理流程：

1. 用户在文件树中点击文件。
2. 主进程读取对应的 `.enc` blob。
3. 解包 DEK，解密内容到内存。
4. 小文件经 IPC 传 ArrayBuffer、大文件经 `vault://` 流式供给（见 §6.3）。
5. 渲染进程根据文件扩展名选择对应的预览组件。
6. 关闭预览时销毁 Blob URL（`revokeObjectURL`）和 DOM 元素，主进程 `Buffer.fill(0)` 清空。

**预览组件一律用自定义协议 `vault://` 加载，不用 `file://`。** 理由见 §10。

## 6.3 大文件预览通道（`vault://` 流式协议）

**问题：** Electron 的 IPC 走结构化克隆，传几十 MB 的 ArrayBuffer 会有明显卡顿，且主进程一份、渲染进程一份，内存占用翻倍。

**规则：**

| 文件大小 | 通道 |
|---|---|
| ≤ 16MB | IPC 传 ArrayBuffer（简单，够用） |
| > 16MB | 自定义协议 `vault://blob/{blobId}`，边解密边流式返回 |

**实现方式：**

```javascript
protocol.registerBufferProtocol('vault', async (request, callback) => {
  const blobId = parseId(request.url);
  const meta = { mimeType: lookupMime(blobId) };
  // 流式解密：读一块 → 解一块 → 回调一块，不把整个文件读进内存
  const stream = createDecryptStream(blobId);
  callback({ statusCode: 200, headers: { 'Content-Type': meta.mimeType }, data: stream });
});
```

渲染侧直接把 URL 交给原生标签消费，明文不经过 JS 大对象：

```html
<img   src="vault://blob/{id}">
<audio src="vault://blob/{id}" controls>
<video src="vault://blob/{id}" controls>
```

**注意点：**

- 协议必须校验请求来源（只允许来自本应用自身的窗口），不能让任意网页通过 `vault://` 读到明文；
- 协议必须支持 `Range` 请求，否则音视频无法拖动进度条；
- 锁定/退出时立即注销协议句柄并清空解密缓冲；
- 整文件模式下虽然是一次性加密，但解密仍可分块流式返回（解密一块吐一块），内存峰值可控。

对于音视频和图片等较大文件，可以支持流式解密以减少内存峰值：

```
加密文件 → 读取块 → AES-GCM 解密块 → 流式传给预览组件
```

说明：OnlyOffice WASM 的社区方案（如 pi-view-port）已经支持 PDF、Markdown、HTML、图片、视频、音频和 Office 文档的统一预览。如果该方案满足需求，可以复用其统一预览层，减少自研工作量。

## 7. 自动锁屏设计

### 7.1 状态管理

- `unlocked`：已解锁，masterKey 在内存。
- `locked`：已锁定，masterKey 已清空，manifest 明文已清空。

### 7.2 主进程实现

```javascript
// 伪代码
const { powerMonitor } = require('electron');

let lastActivityTime = Date.now();
let autoLockMinutes = config.autoLockMinutes; // 0 表示从不

// 定时检查
setInterval(() => {
  if (autoLockMinutes > 0 &&
      Date.now() - lastActivityTime > autoLockMinutes * 60 * 1000) {
    lockVault();
  }
}, 10000);

// 系统事件
powerMonitor.on('suspend', () => lockVault());
powerMonitor.on('lock-screen', () => lockVault());

function lockVault() {
  masterKey.fill(0);
  masterKey = null;
  manifestPlain = null;
  // 通知渲染进程显示锁屏遮罩
  mainWindow.webContents.send('vault-locked');
}
```

### 7.3 渲染进程

- 监听鼠标、键盘、触摸事件，节流上报活动时间给主进程。
- 收到锁定通知后：卸载预览组件 → 清空 Blob → 显示锁屏遮罩 → 聚焦密码输入框。

### 7.4 配置项

```json
{
  "autoLockMinutes": 5,
  "lockOnBlur": false,
  "lockOnSuspend": true,
  "clearClipboardOnLock": true,
  "closePreviewOnLock": true
}
```

`autoLockMinutes`：0 表示从不，用户可在设置界面修改。

`lockOnSuspend`：系统休眠/睡眠时自动锁定。

### 8.1 通用二进制构建

使用 electron-builder 构建 macOS 通用二进制：

- 或右键点击应用，选择"打开"。

### 8.4 注意事项

- **勘误：** Electron 在 macOS 上使用的同样是 Chromium/Blink，**不存在"WebKit 与 Chromium 的 WASM 差异"**——原文档的这一判断不成立，不必为此准备备选方案。
- 真正的平台差异在于：Apple Silicon 上 WASM 的内存上限与 JIT 策略、以及未签名应用是否受 hardened runtime 限制。**需要在真实的 Intel Mac 与 Apple Silicon Mac 上分别实测 OnlyOffice WASM 的渲染表现与内存占用**，这是唯一可靠的验证方式。
- 若实测发现 WASM 在 macOS 上不稳定，备选方案是本地集成 LibreOffice 无头模式转 PDF 后走 PDF 通道预览。
- **不要在 `.app` 包内部写入任何用户数据**：往包内写文件会破坏 ad-hoc 签名，可能触发比"无法验证开发者"更难处理的 Gatekeeper 拦截；且只读介质（DMG 挂载、部分 U 盘）上会直接失败。
- `config.json` 优先写在 `.app` **同级目录**（保持便携），不可写时回退到 `~/Library/Application Support/BabyBus/`。
- 文件库由用户自行选择位置，与 `.app` 完全解耦，因此不存在包内写数据的问题。需在界面上明确展示当前文件库的完整路径，方便用户自己备份。

## 9. 软件更新机制

### 9.1 更新架构

本软件为绿色免安装版本，更新流程与安装版不同。

**P0-2 决策：本软件不具备任何网络能力，不设更新检测接口。**

```
┌─────────────────────────────────────────────────┐
│  本程序：零网络请求                               │
│  ├─ 无更新检测接口                               │
│  ├─ 无崩溃上报                                   │
│  ├─ 无版本/激活/埋点上报                          │
│  └─ 无远程资源加载                               │
└─────────────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────────┐
│  用户手动更新                                     │
│  1. 设置 →「前往官网查看更新」                     │
│     （shell.openExternal，由系统浏览器打开）       │
│  2. 下载新版 ZIP                                 │
│  3. 解压到新目录                                  │
│  4. 启动新版，「打开文件库」选中原位置              │
│  5. 无需复制任何数据                              │
└─────────────────────────────────────────────────┘
```

> 原方案里的"软件内检查更新"已取消。一个加密软件只要保留一条联网通道，用户就无法验证它到底传了什么——**去掉全部网络能力，是"不联网"这个承诺能被真正兑现的唯一方式。** 代价是用户需要手动看官网，这个代价值得。

### 9.2 官网发布页（由浏览器打开，本程序不参与）

发布页需要提供：最新版本号、发布日期、各平台 ZIP 下载链接、**发布包的 SHA-256 校验值**、更新说明。

```
https://example.com/releases

  宝宝巴士-green-win-x64.zip            sha256: ...
  宝宝巴士-green-macos-universal.zip    sha256: ...
```

> **校验值是必需的。** 用户从网页下载 ZIP，如果页面不提供哈希，就没有办法验证下载到的是不是被替换过的包。这是去掉自动更新后必须补上的一环。
>
> 程序内同样提供「校验本地安装包」的小工具（选择 ZIP 文件 → 计算 SHA-256 → 与官网值比对），全程离线。

### 9.3 客户端实现

```javascript
// 设置 → 「前往官网查看更新」
// 只做一件事：用系统默认浏览器打开发布页。本程序自身不发起任何请求。
const { shell, app } = require('electron');

function openReleasePage() {
  shell.openExternal(RELEASE_PAGE_URL);
}

// 附带：离线校验下载包的 SHA-256
const { createHash } = require('node:crypto');
const fs = require('node:fs');

async function sha256OfFile(filePath) {
  const hash = createHash('sha256');
  for await (const chunk of fs.createReadStream(filePath)) hash.update(chunk);
  return hash.digest('hex');
}
```

**禁止事项（写进代码评审清单）：**

- 不得引入 `net` / `http` / `https` / `fetch` 做任何主动请求；
- 不得集成任何统计、遥测、崩溃上报 SDK；
- 渲染进程 CSP 设置为 `default-src 'none'`，从策略层面封死联网可能（见 §10）。

### 9.4 数据兼容性保证

- 文件库格式（`vault.meta` / `manifest.enc` / `blobs`）在版本间保持向后兼容，与文件库存放位置无关。
- `vault.meta` 中包含 `version` 字段，用于未来可能的格式升级。
- 如果新版本引入了新的 vault 格式，软件在首次打开时会提示升级，并自动备份旧数据。

### 9.5 关于 electron-updater

标准的 electron-updater 方案适用于安装版应用（通过 Squirrel 或 NSIS 安装），它会自动下载更新包并替换应用文件。但对于绿色免安装版本，自动替换运行中的文件存在权限和文件锁的问题，因此推荐使用手动更新 + 数据目录迁移的方式，更加可靠且用户可控。

## 10. 安全加固

| 措施 | 说明 |
|---|---|
| `contextIsolation: true` | 渲染进程与主进程上下文隔离 |
| `nodeIntegration: false` | 渲染进程无法直接访问 Node.js |
| `sandbox: true` | 启用沙箱 |
| preload 最小 API | 仅暴露必要的 IPC 接口 |
| IPC 参数校验 | 严格校验所有 IPC 传入参数 |
| 禁止外部导航 | 阻止渲染进程跳转到外部 URL，外链一律交给 `shell.openExternal` |
| CSP `default-src 'none'` | 彻底封死联网可能（P0-2 决策：零网络能力） |
| 校验 IPC 发送方 | 校验 `event.senderFrame` 的来源，不只看 `BrowserWindow` |
| 用自定义协议替代 `file://` | 预览页走 `vault://`，避免 `file://` 带来的本地文件读取面 |
| 主密钥仅内存 | masterKey 只存在于主进程内存 |
| 锁定即清空 | 锁定后立即清空密钥和解密数据 |
| 日志脱敏 | 不记录密码、密钥、文件内容 |

## 12. 主要风险与应对

| 风险 | 应对 |
|---|---|
| 文件库路径失效（U 盘拔出/文件夹被移动） | 提示"未找到文件库"并提供重新选择，**绝不静默新建** |
| 在已有库上误点"新建"导致 vault.meta 被覆盖 | 新建前强制校验 `vault.meta` 是否存在，存在则强制走"打开"流程 |
| 文件库放网盘同步目录，多端并发写 manifest | 建议单端使用；manifest 写入采用临时文件 + 原子 rename |
| Apple Silicon 上 WASM 渲染/内存表现 | 真机实测（Intel + Apple Silicon 各一台），备选 LibreOffice 无头转 PDF |
| 大文件流式解密内存峰值 | >16MB 走 `vault://` 流式，边解边传；`ENC1` 已预留分块字段 |
| manifest 大库时重写性能 | 超大规模时引入增量 manifest 或分片；当前整体重写 + 原子替换 |
| 放弃 Win7/8 导致部分老用户无法安装 | 安装时检测系统版本并给出友好提示；不提供旧系统专用版本 |
| Electron 版本迭代快 | 跟随稳定线，定期升级；关注 Chromium 安全公告 |
| 绿色版更新文件替换冲突 | 采用手动更新 + 文件库位置不变，程序与数据解耦 |
| 内置 Argon2 在目标环境不可用 | M0 阶段做能力探测；不可用则回退 scrypt 并如实写 `kdf` 字段 |
| 主密码忘记 | 无法恢复，首次设置强提示 |
| AGPLv3 许可证 | 商业分发前评估 OnlyOffice 商业许可 |
| macOS 公证与签名 | 绿色版跳过，用户手动信任；商业版需签名 |

## 13. 更新与新增功能总结

| 修改项 | 方案 |
|---|---|
| 文件库定位 | **取消默认路径，不支持自动建库**；用户显式新建/打开文件库，程序与数据完全解耦 |
| 软件更新 | **零网络能力**，无更新检测接口；官网发布页 + SHA-256 校验 + 手动替换 ZIP，文件库位置不变 |
| 加密安全性 | AES-256-GCM + Argon2id（**Electron 下走 hash-wasm**，内置可用时优先内置，末位 scrypt 兜底）、信封加密、**AAD 绑定** |
| blob 格式 | `ENC1` v2：Header（含 blobId / plainSize）+ wrappedDEK 段 + content 段，**预留分块字段** |
| 解锁方式 | 仅主密码（**已确认取消密钥文件/U 盘双因子**） |
| 文件操作 | 新增**删除（直接销毁不进回收站）、重命名、搜索（仅文件名）、修改主密码** |
| 导入行为 | **默认保留原始文件**，由用户自行决定是否删除；文档中说明擦除在 SSD/网盘上不可靠 |
| 大文件预览 | >16MB 走自定义 `vault://` 协议流式返回，支持 Range 请求 |
| manifest 写入 | 临时文件 + fsync + 原子 rename + 保留 `.bak`，启动校验失败自动回退 |
| 桌面框架 | **Electron 43.x**（放弃 Win7/8，换回持续安全更新）；Win10+ / macOS 13+ |
| macOS 支持 | electron-builder --universal（内部走 @electron/universal），须在 macOS 主机构建 |
| TXT 预览 | 渲染进程直接显示纯文本 |
| 图片预览 | 解密后 Blob URL + `<img>` 标签 |
| 音频预览 | 解密后 Blob URL + `<audio controls>` 播放 |
| Markdown 预览 | marked 或 markdown-it 渲染为 HTML |
