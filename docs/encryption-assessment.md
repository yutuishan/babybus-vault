# 加密强度评估：从发行版目录能推出什么、能不能破解

**评估对象**：宝宝巴士（babybus-vault）v0.1.0
**评估方式**：直接审阅发行版目录内的代码文件与配置文件
**评估日期**：2026-09-12

---

## 一、结论先说

| 攻击场景 | 能推出加密方式吗 | 能破解吗 |
| --- | --- | --- |
| **只有文件库，没有客户端** | **能，但有限** | **不能** |
| **既有绿色版客户端，又有对应文件库** | **能，且很完整** | **不能** |

两句话总结：

1. **加密方式在设计上就不保密，也从来没打算保密。** 算法、参数、文件格式全部可读、全部写在磁盘上。这不构成缺陷 —— 现代密码学的安全性建立在"密钥保密"上，而不是"算法保密"（Kerckhoffs 原则）。
2. **真正拦住攻击者的那道墙是 Argon2id + 主密码的熵。** 拿到全部代码和全部密文之后，攻击者唯一能做的就是暴力枚举主密码。这道墙没有捷径可走。

---

## 二、场景 A：只有文件库，没有客户端

攻击者手上只有一个文件夹，里面长这样：

```
我的文件库/
├── vault.meta          # 明文 JSON
├── manifest.enc        # 加密的目录树
├── manifest.enc.bak    # 上一版备份（同样是密文）
└── blobs/
    ├── 3f2a…c8.enc     # 每个文件一份密文
    └── 91b7…04.enc
```

### 2.1 直接从 vault.meta 读出来的信息

`vault.meta` 是**明文 JSON**，不需要任何凭据就能打开：

```json
{
  "version": 3,
  "kdf": "argon2id",
  "kdfImpl": "hash-wasm",
  "kdfParams": { "memory": 65536, "passes": 3, "parallelism": 1, "tagLength": 32 },
  "salt": "kR2x…（16 字节 base64）",
  "verify": {
    "nonce": "…（12 字节）",
    "ciphertext": "…（12 字节，固定明文 'unlock-check'）",
    "tag": "…（16 字节）"
  }
}
```

由此可确定：

| 项 | 能推出吗 | 说明 |
| --- | --- | --- |
| 密钥派生算法 | ✅ | `argon2id` |
| KDF 参数 | ✅ | 64 MiB 内存 / 3 轮 / 并行度 1 |
| 盐 | ✅ | 明文存储（必须的，否则无法复现派生） |
| 校验机制 | ✅ | AES-256-GCM 加密固定串 `unlock-check`，再经 HKDF 派生独立校验密钥 |
| 内容加密算法 | ✅（推测） | 从 `blobs/*.enc` 头部魔数、密文结构与长度可推断 AES-256-GCM 信封模式 |
| 是否有后门 | ✅ | 没有。可执行文件与代码全量审计未见任何联网、外发、隐藏密钥逻辑 |
| **主密码 / 主密钥** | ❌ | **不可能得到** |

### 2.2 从 blobs 二进制布局能读出来的

blob 头部是**明文**（38 字节），承载解密所需的元信息：

| 偏移 | 长度 | 字段 | 敏感度 |
| --- | --- | --- | --- |
| 0 | 4 | magic `ENC1` | 非敏感 |
| 4 | 1 | 版本 `2` | 非敏感 |
| 5 | 1 | flags（整文件/分块） | 非敏感 |
| 6 | 4 | chunkSize | 非敏感 |
| 10 | 4 | chunkCount | 非敏感 |
| 14 | 16 | blobId（UUIDv4） | 非敏感，但可关联 manifest |
| 30 | 8 | **plainSize（明文字节数）** | **会泄露文件原始大小** |

后面依次是 `wrappedDEK`（60 字节）、`contentNonce`（12）、`contentTag`（16）、`contentCiphertext`（变长）。

值得注意的两点：

- **文件名与目录结构完全不可见。** 全在这份库里唯一的密文 `manifest.enc` 里。这也解释了为什么项目把 manifest 的原子写入当成头号风险 —— 它一坏，密文还在但没人知道谁是谁。
- **唯一泄露的元数据是每个文件的明文大小**（`plainSize` 字段 + 密文长度）。文件名列表拿不到。
- 还有一个**全局可关联性**：`blobId` 是明文 UUID，配合 manifest 的密文结构，攻击者能把"哪些文件长期没变、哪些新增"这类模式看出来。属于可接受的元数据泄露，但应当知道它存在。

### 2.3 结论

只有文件库时，攻击者能完整重建**加密方案的全部规格**，但拿不到主密码、主密钥、文件名、文件内容。**无法破解。**

## 三、场景 B：绿色版客户端 + 对应文件库

多出来的是一整个客户端目录，里面有可执行文件、`app.asar`、源代码与配置。

### 3.1 多出来的关键信息

审阅代码可以拿到完整的实现细节，其中有些是场景 A 里只能猜的：

1. **HKDF 的用途标识常量**——这是最关键的一项：
   - `vault-manifest-v1` → manifest 的加密密钥
   - `vault-verify-v1` → vault.meta 校验值的密钥
2. **子密钥派生链**：`masterKey = Argon2id(password, salt)` → `subkey = HKDF-SHA256(masterKey, salt, info)`
3. **AAD 的具体构造**：blob 的 `wrappedDEK` 与 `content` 都以 38 字节 header 为 AAD；manifest 以字符串 `manifest-v2` 为 AAD
4. **nonce 长度（12）、tag 长度（16）、DEK 长度（32）、wrappedDEK 段定长（60）**
5. **"改主密码不重加密内容"的设计**：只重写 wrappedDEK 段
6. **密码策略**（前后端双重校验的规则）

### 3.2 有了这些，攻击者能做什么？

**能做的更多，但依然卡在同一道墙上。**

把上述全部细节拼起来，攻击者可以写一个完整的离线破解器：

```
对候选密码 p:
  mk = Argon2id(p, salt, memory=65536, passes=3, parallelism=1, tagLength=32)
  vk = HKDF-SHA256(mk, salt, "vault-verify-v1", 32)
  用 vk 解 vault.meta 的 verify 段，比对明文是否等于 "unlock-check"
  命中 → mk 正确 → 再派生 "vault-manifest-v1" 解开目录树
```

这个破解器**可以本地高速跑**，不需要客户端、不需要联网。但它毫无"聪明"可言 —— 它只是逐个试密码。**一份完整、准确的算法规格，价值在于让暴力枚举跑得规范，而不在于绕过加密本身。**

### 3.3 三点值得单独说明

**（1）`kdfImpl` 字段不构成风险。**
代码里记录了当前环境用的是哪个 Argon2id 实现（Electron 走 hash-wasm，因为 BoringSSL 不支持 `crypto.argon2Sync`）。关键是**两种实现在同一组参数下输出逐字节一致**，已被项目自带测试验证。所以 `kdfImpl` 只是一个"这台机器当时用谁算的"的提示，不影响互操作性，也不降低强度。

**（2）校验值设计得很克制。**
`verify` 用 HKDF 派生出独立密钥再加密固定串，而不是用主密钥直接加密一个已知明文。这个区别很重要：后者相当于白送攻击者一组 `(明密文对)`，虽然 AES-GCM 本身仍能抗住，但没有任何理由主动增加暴露面。项目在这里做对了，并在代码注释里明确写了理由。

**（3）AAD 绑定 header 而非整个 wrappedDEK 段，是一个有意的取舍。**
代码注释解释了原因：若 AAD 并上 wrappedDEK 段，则改主密码必然改变该段字节，进而使 content 的 AAD 失效 —— 那就必须重加密全部文件内容，与"瞬间完成改密码"的承诺直接冲突。跨文件搬运攻击已由 header 里的 `blobId` 阻断，因此这个取舍不损失实际安全性。**这是一个经得起推敲的决定，不是疏忽。**

### 3.4 结论

有客户端 + 文件库时，攻击者能完整重建加密方案（含 HKDF 标签、AAD 构造、所有长度常量），并可据此写出规范的离线暴力破解器。但**依然无法破解** —— 所有路径最终都归到"猜出主密码"。

## 四、真正的风险面在哪

既然两种场景都破不了，那风险实际落在哪里？

| 风险 | 说明 | 现有缓解 |
| --- | --- | --- |
| **主密码太弱** | 唯一实质性的攻击面。口令熵不够时，Argon2id 只能把每次尝试的成本抬高，不能阻止穷举 | Argon2id 64 MiB / 3 轮（OWASP 推荐档位）；创建时强制"≥8 位 + 含字母 + 含数字" |
| **明文在内存中** | 解锁后主密钥与解密内容都在进程内存里，内存转储 / 调试器可获取 | 用后 `wipe()` 清零；`renderer` 侧用完即弃并 revoke |
| **元数据泄露** | 文件数量、每个文件的明文大小、变更时序 | 未处理（属可接受范围，但应知晓） |
| **客户端被篡改** | 攻击者替换绿色版客户端，在密码输入处埋点 | 无签名/校验机制 —— **绿色版分发天生缺少这一环** |
| **Argon2id 依赖回退到 scrypt** | 极老环境可能落到 scrypt | 有明确的能力探测与显式回退，且参数会写进 vault.meta |

**最需要用户理解的一条**：算法和参数公开完全没问题；破解的唯一门径是猜主密码。所以**主密码的强度就是全部的安全性**。

## 五、给使用者的建议

1. **主密码用长口令，别用 8 位短密码。** 建议 4 个以上不相关的词，或 ≥16 位随机串。Argon2id 挡得住"随便猜"，挡不住"弱口令"。
2. **绿色版客户端要保护来源。** 在有攻击者能替换你客户端的场景下，任何本地加密软件都防不住 —— 这是分发方式决定的，不是本软件特有的问题。请从可信渠道获取，并核对文件哈希。
3. **不要把 vault.meta 和 blobs 当敏感数据删或改。** 它们不含秘密，但删了会导致数据无法恢复。
4. **备份 manifest.enc。** 它是唯一存有文件名与目录结构的密文，坏了就等于"密文还在但不知道谁是谁"。
5. **共享文件库时不必担心泄露算法**，但要意识到共享即可被离线暴力枚举，因此共享对象的主密码强度尤其重要。

---

## 六、可直接引用的判定

> 从发行版目录中的代码文件与配置文件，**攻击者可以完整推断出本软件的加密方案**——包括密钥派生算法与参数、子密钥派生标签、AAD 构造、文件容器格式与全部长度常量。
>
> 但**无法据此破解**。所有攻击路径最终都归结为对 Argon2id 保护下的主密码进行暴力枚举，这需要实际猜测出主密码，无法通过算法知识绕过。
>
> 唯一实质性的风险来自**主密码本身的强度**，而非方案的可推导性。
